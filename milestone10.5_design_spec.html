Task 2 — Live Capture Recommendation (hypothesis tested, not accepted)

The initial hypothesis (5-min capture 14:30–14:49, 1-min capture 14:50–15:15) is REJECTED as a forward recommendation — not because it's unsafe, but because it would be a downgrade from what the live pipeline already does for free. Task 1's full-day query shows option-chain snapshots are already being captured at ~1-minute density across the entire session (09:15–15:27), including 14:30–14:49. Deliberately coarsening to 5-minute capture in that sub-window would discard real, currently-free data with zero cost saved (no new Dhan calls are triggered either way — this is a resolution choice at the derivation/query layer, not the capture layer).

Revised recommendation:

  • 14:30–15:15 (and, per the full-day finding, the rest of the session too): keep 1-minute derivation resolution. This is already happening at the capture layer — no pipeline change needed, only continuing to derive features at 1-minute density from what's already stored, as Milestone 9/10 already did.
  • Where sparser sampling is genuinely fine (Milestone 10 Part 18 finding, re-confirmed structurally here): PCR-based features are insensitive to sampling frequency (typical 1-min noise ≈ 0.001, 5-min staleness ≈ 0.002) — an analysis pipeline that only evaluates PCR at 5-min checkpoints loses essentially nothing. IV skew and ATM straddle value are the two features that need the finer 1-minute resolution to avoid understating their true intraday range (staleness roughly triples between 1-min and end-of-window-only sampling).
  • No new Dhan API calls are needed for Milestone 11. The recommendation is entirely about which resolution the research/backtest layer reads at — the capture layer is already sufficient and should not be touched.

Task 4 — Walk-Forward Validation Design

Milestone 10's 58.7% options-only accuracy was computed in-sample — the median thresholds that define "vote up" were fit using all 46 days, including the same days being scored. This number must now be relabeled a discovery-set baseline, not a validated result, exactly as this milestone's brief requires.

Chronological split (23 unique trading dates, 46 symbol-days, both symbols share every date)

TierDatesSymbol-daysPurpose
Training2026-08-03 → 2026-08-21 (14 dates)28Fit baseline thresholds (medians) and evaluate each candidate incremental feature's raw effect
Validation2026-08-24 → 2026-08-31 (5 dates)10Decide, one feature at a time, whether each Task-5 candidate feature is kept in the model — thresholds still come only from Training
Test (held out, touched once)2026-09-01 → 2026-09-04 (4 dates)8Final, single evaluation of the locked model — no further tuning after this is seen
Every threshold (medians, etc.) used to score a Validation or Test day must be computed using only Training-tier data — this is the one concrete mechanical fix from Milestone 10's in-sample number. A day's own value is never used to help classify itself.

Honest caveat on statistical power

An 8-day test set means even a genuinely 60%-accurate model could show anywhere from ~25% to ~90% accuracy on Test purely from binomial sampling noise at this N. A single Test-tier accuracy number from Milestone 11 must not be treated as conclusive — it's a necessary discipline step (avoids re-using Training data to grade the final model), not a claim that 8 or 10 days is enough to prove or disprove the model.

Path to real walk-forward (once N grows)

A true expanding-window walk-forward (retrain thresholds after every new day, test on the next single day, roll forward) is the more statistically honest design long-term, and is exactly how the market_transition/scoring.py::find_analogs k-NN engine could naturally operate day-by-day. It's not proposed as Milestone 11's primary method because with daily granularity and only 46 days, each "fold" would be a single test day — too noisy to interpret in isolation, and no better than the static Test tier above at this sample size. Recommendation: adopt the static 3-way split now; switch to rolling walk-forward once the option-covered sample passes roughly 90–120 symbol-days (4–6 more months of live capture) — a concrete, sample-size-justified trigger rather than an arbitrary later date.

Task 5 — Direction Baseline & Incremental Feature Plan

Frozen baseline (exact definition, not to be modified)

FeatureVote signRule
PCR (OI)−1vote UP if pcr_oi < median(pcr_oi | Training)
Call/Put volume imbalance+1vote UP if value > Training median
ATM straddle change+1vote UP if value > Training median

Final call = majority sign of the three votes (matches Milestone 10's Model B exactly, with the one leakage fix: medians from Training only).

Incremental feature-testing plan

Each candidate is added to the frozen baseline one at a time, scored on Validation only (thresholds still fit on Training), and kept only if it improves Validation accuracy over the frozen 3-feature baseline. Order reflects Milestone 10's own evidence (strongest prior signal first):

  1. IV skew — Milestone 10 Part 6 showed this is the one feature that meaningfully sharpens near 14:59; test whether adding it improves on the (early-and-stable) PCR-driven baseline.
  2. 1-minute option-state changes (trajectory features from Task 3's new 14:50→14:59 slice) — tests whether the shape of the last 10 minutes (accelerating vs. decelerating PCR/IV) adds information beyond a single 14:59 level.
  3. Price/options divergence flag (Milestone 10 Part 10: agree vs. disagree) — tests whether explicitly modeling the 70%-of-days divergence case (where options-vote alone was right 59.4% of the time) beats implicitly ignoring it.
  4. OI change, PCR change, straddle-change trajectory — incremental versions of already-used levels; tests whether the rate of change adds signal beyond the level.
  5. Position classification (BULLISH/BEARISH/NEUTRAL/MIXED/RAPIDLY_CHANGING, Milestone 9) — tests whether the categorical synthesis label adds anything beyond its own inputs.
  6. Expiry regime (weekly vs. monthly) — given Task 1's confirmed thin per-expiry N, expect this to be flagged INSUFFICIENT DATA rather than accepted or rejected outright.

A feature that fails to improve Validation accuracy is dropped, not forced in — matching Milestone 10's own finding that combining features can hurt (Model C underperformed Model B).

Task 8 — Expected Move → Option Opportunity Methodology

Conceptual scoring design (not implemented): given the existing unified forecast's probability_up/probability_down/probability_flat and expected_move_low/high (Milestone 9, reused read-only, never modified), score each ATM±5 candidate by:

opportunity_score(candidate) = P(favorable direction) # from the unified forecast, not re-derived × expected_intrinsic_gain(expected_move, candidate.delta, candidate.strike) # linear delta-approximation of payoff at the expected move − theta_decay_cost(candidate.theta, holding_minutes=15) # known, deterministic cost over the 15-min horizon − iv_crush_risk(candidate.vega, iv_regime) # only a qualitative flag today -- no historical IV-crush-at-3pm study exists yet − spread_cost_pct(candidate.spread_pct) # realistic round-trip execution cost , gated to zero whenever liquidity/data-quality checks (Task 9) fail

This is a documented, interpretable heuristic formula to be back-tested against Task 6/7's dataset in Milestone 11 — not a fitted model, per this project's established stance on small-sample research. Its inputs (delta, theta, vega, IV, spread, premium, moneyness, liquidity) are all already captured; what's new is the combination formula itself, which must be validated exactly like Task 5's incremental features (Training→Validation→Test), not accepted on inspection.

Task 10 — Final Deliverable Summary

  1. Data-readiness report: Task 1 above — underlying data 100% complete (50/50 symbol-days); option data 46/50 symbol-days usable, ≥90% minute-complete in every case; ATM±5/bid-ask/IV/OI structurally always present; greeks degenerate on ~19% of deep-ITM puts (disclosed, not fixed); expiry cells still too thin for a standalone conclusion.
  2. Recommended capture frequency: Task 2 — keep 1-minute derivation resolution throughout the session (already the case at the capture layer, zero new cost); no case found for coarsening any part of 14:30–15:15 to 5-minute.
  3. Research dataset specification: Task 3 — a single versioned pickle, two physically separate build paths (pre-14:59 features vs. post-15:00 outcomes) to make timestamp leakage structurally hard to introduce.
  4. Walk-forward validation methodology: Task 4 — static chronological 28/10/8 symbol-day Training/Validation/Test split now; graduate to a rolling expanding-window design once the option-covered sample passes ~90–120 symbol-days.
  5. Direction baseline specification: Task 5 — Milestone 10's exact 3-feature median-split vote, frozen, re-fit only on Training-tier medians (the one concrete leakage correction).
  6. Incremental feature-testing plan: Task 5 — 6 candidates, tested one at a time against Validation, kept only on demonstrated improvement.
  7. Option candidate specification: Task 6 — ATM±5 × {CE,PE}, ask-entry/bid-exit, all needed fields already captured or one-line derivable.
  8. Strike-selection methodology: Task 7 — 7-bucket structure, return/win-rate/MFE/MAE/spread/risk-reward per symbol; NIFTY and SENSEX show opposite-shaped patterns — reported, not resolved into a rule.
  9. Expected-move-to-option methodology: Task 8 — a documented, interpretable opportunity-score formula combining the existing forecast's probabilities/expected-move with delta/theta/vega/IV/spread — to be validated, not assumed.
  10. NO-TRADE framework: Task 9 — 8 explicit, checkable conditions, each tied to a concrete threshold and a specific piece of already-measured evidence.
  11. Milestone 11 implementation plan (order of build):
    1. Build the Task 3 research dataset (pure derivation from already-reconstructed Milestone 9/10 pickles + one new 14:50→14:59 trajectory slice) — no new DB reads beyond what Milestone 10 already queries.
    2. Implement the Task 4 chronological split and re-fit the Task 5 baseline's thresholds on Training only; report the corrected (no-longer-in-sample) accuracy on Validation as the first real result.
    3. Run the Task 5 incremental-feature loop against Validation, one feature at a time; lock the final feature set.
    4. Evaluate the locked model on Test exactly once; report the result with its (wide, small-N) confidence caveat explicit.
    5. Only then build the Task 6/7/8 option-opportunity scoring on top of whichever direction signal survived Test — scoring an option candidate before the direction signal is validated would be building on an unvalidated foundation.
    6. Wire in the Task 9 NO-TRADE gate last, since it depends on thresholds (analog depth, spread, opportunity score) that only exist once steps 1–5 are complete.

Final Question

Are we ready to implement Milestone 11, and exactly what should be implemented first?

Yes, ready to implement — but only the first three steps of the plan above, not the whole engine at once. The data is genuinely sufficient to attempt a proper out-of-sample test (Task 1 found no material data gap that would block it), and Milestone 10 already produced a specific, falsifiable baseline (58.7% options-only vote) worth re-testing honestly. But that baseline has never been evaluated out-of-sample, and everything downstream — strike selection, the opportunity score, the NO-TRADE gate — depends on knowing whether it survives that test.

Build first, and only: the Task 3 dataset + the Task 4 chronological split + a Training-only re-fit of the Task 5 baseline, reporting its Validation-tier accuracy. That single number is the actual pivot point for this whole research line — if the baseline holds up out-of-sample (even at a reduced accuracy), the incremental-feature and option-opportunity work is worth doing; if it collapses toward 50% out-of-sample, that is itself the most important, honest finding Milestone 11 could produce, and building the option-opportunity engine on top of a signal that doesn't survive its first out-of-sample test would not be a responsible next step.
