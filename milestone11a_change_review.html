What changed, in one paragraph

Milestone 10 reported 58.7% accuracy for an options-only directional vote, but that number was in-sample — the thresholds that decide "vote up" were computed using all 46 days, including the very days being scored. Milestone 11A builds the actual out-of-sample test: a research dataset (2:59pm decision-side features, kept physically separate from the 3:00–3:15pm actual outcome), a strict chronological Training/Validation/Test split, and a re-fit of the exact same, frozen Milestone 10 baseline using thresholds derived from Training data only. Nothing about the baseline itself was changed — three features, same signs, same majority vote — only how its thresholds are computed and which days are used to test it.

The only change to an existing file — db/reader.py

def load_actual_outcome_all_horizons(symbol: str, session_date: date) -> dict[int, dict]:
    """All persisted transition_actual_outcome rows (every horizon: 1/5/10/15
    minutes) for `symbol`/`session_date`, keyed by horizon_minutes -- used by
    scripts/run_milestone11a.py to build the post-cutoff (>=15:00) outcome
    half of the Milestone 11A research dataset. Read-only; never called by
    anything that also touches pre-cutoff (<=14:59) data, so it cannot be a
    leakage vector on its own."""
    rows = fetch_all(
        f"SELECT {', '.join(_ACTUAL_OUTCOME_ALL_COLUMNS)} FROM transition_actual_outcome "
        "WHERE symbol = %s AND session_date = %s ORDER BY horizon_minutes",
        (symbol, session_date),
    )
    result = {}
    for r in rows:
        d = dict(zip(_ACTUAL_OUTCOME_ALL_COLUMNS, r))
        result[d["horizon_minutes"]] = d
    return result

A pure SELECT, no writes, added alongside the existing (unmodified) load_actual_outcome().

Design: how leakage is prevented

  • Two physically separate builders. build_pre_cutoff_features() only ever calls the DB with cutoff times ≤14:59:00 (enforced by db.reader.get_option_chain_raw_near's own SQL filter, and separately by this module's fixed 8-checkpoint/10-trajectory-minute constant lists — neither list contains a time past 14:59). build_post_cutoff_outcomes() takes no candle or option data at all — only already-fetched outcome rows — so it has no path by which pre-cutoff data could leak in.
  • Column-namespace collision guard. merge_pre_post() raises if any key overlaps between the two halves — the `under_`/`opt_`/`traj_` and `actual_` prefixes are disjoint by construction.
  • Training-only thresholds. fit_thresholds() only ever sees the exact list it's handed — the orchestrator passes it df[tier=="training"] and nothing else; Validation and Test are scored with that same frozen dict, never re-fit.
  • Real bug caught during this build: get_option_chain_raw_near falls back to the latest snapshot at/before 14:59 no matter how much earlier in the day that is. Two days (NIFTY/SENSEX 08-18, NIFTY/SENSEX 08-26) had no real 14:30–15:15 option capture, and would have silently scored using a stale snapshot (one over 2 hours old) mislabeled as "the 14:59 state." Added a staleness check (opt_1459_stale, >180s old) and excluded those 4 symbol-days rather than fabricating a decision from stale data — this exactly reproduces Milestone 10.5's independently-measured "46 of 50 usable" finding.
