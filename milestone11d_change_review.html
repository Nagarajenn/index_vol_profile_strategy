Safety statement first. The paper engine cannot place a real order. There are zero references to place_order, modify_order, cancel_order, buy_order, sell_order, the Dhan broker client, or dhanhq anywhere in paper_trading/, and a test asserts this by scanning the package's own source on every run. The backend API that feeds the Command Center is registered allow_methods=["GET"], so no action taken in the UI can cause a trade of any kind, paper or real. There is no "Go Live" button and no code path that could become one without a deliberate new milestone.
This is not evidence of profitability. Milestones 11A–11C found no validated directional edge and no validated option-expression rule. The paper agent exists to test whether the platform reads the market coherently, knows when not to trade, and manages risk sensibly — not to make money. All P&L is PRE-COST: no brokerage or tax model exists in this project, so none was invented.

H. Agent state machine

PRE_MARKET -> MARKET_MONITORING -> PRE_14_59_ANALYSIS -> DECISION_FREEZE
                                                              |
                                            +-----------------+-----------------+
                                            v                                   v
                                         NO_TRADE                          TRADE_APPROVED
                                            |                                   v
                                            |                              PAPER_ENTRY
                                            |                                   v
                                            |                          POSITION_MANAGEMENT
                                            |                                   v
                                            |                              PAPER_EXIT
                                            |                                   v
                                            +--------> DAILY_REVIEW <---- TRADE_COMPLETE

PAPER_ENTRY is the only state that opens a position, and it is reachable only from TRADE_APPROVED, which is reachable only from a decision that cleared every gate.

I. Decision methodology — the gate order

Gates are evaluated in a fixed order, so the recorded NO-TRADE reason is always the first disqualifier, never an arbitrary one when several apply. That makes the reason field diagnostic rather than decorative.

#GateReason recorded
1Kill switchKILL_SWITCH_ACTIVE
2Account-level risk block (daily loss / drawdown / trade count)the specific block reason
3Data sufficiencyINSUFFICIENT_DATA
4Option snapshot freshness (> 180 s)STALE_OPTION_DATA
5Conflicting signalsCONFLICTING_SIGNALS
6Actionable trend / confidence / supporting-evidence countLOW_CONFIDENCE, NO_CLEAR_DIRECTION
7Expected move vs ATREXPECTED_MOVE_TOO_SMALL
8Transition riskTRANSITION_RISK_TOO_HIGH
9Option availability (chain, spread, delta, premium)INSUFFICIENT_OPTION_DATA or the selector's own reason
10Risk plan feasibilitySTOP_EXCEEDS_RISK_BUDGET, EXPECTED_REWARD_INSUFFICIENT, PRICE_AT_MAJOR_SUPPORT/RESISTANCE, …
The agent is not a wrapper around 11C. Per the spec, the Milestone 11C option score is deliberately not hard-wired as the trading decision — 11C found no validated option-expression rule, so wiring it in would have shipped an unvalidated rule as if it were validated. The agent instead applies two structural corrections that address 11C's chain-extremes bias: a qualification band (delta floor + premium ceiling) before ranking, and ranking in percentage terms rather than absolute points.

J–N. Trend, option selection, stop, target, management

LayerMethod
J. Trend assessment10 bounded votes wrapping existing analytics (trend classifier, VWAP position and slope, POC, buy/sell dominance, RVOL, PCR, institutional bias, structure proximity, CAS transition forecast). The existing classifier is one input among ten, never replaced. Each vote records a (sign, message) pair; the net score's sign then splits those messages into SUPPORTING and CONFLICTING, so a bullish input can never be listed as supporting a DOWN verdict.
K. Option selectionATM±5 window, direction-matching leg only (CE for UP, PE for DOWN). Qualify on delta ≥ 0.15, premium ≤ ₹600, spread ≤ 3%; then rank the survivors in percentage terms. No symbol-specific strike rule — NIFTY is not hard-coded to OTM, SENSEX is not hard-coded to ITM; both run the identical selector.
L. Dynamic stopUnderlying-first: the nearest structural invalidation level (including soft levels — VWAP, POC, VAL), floored and capped by ATR, then translated to a premium level via delta. Structure leads; ATR only bounds it.
M. Dynamic targetOnly genuine S/R levels (resistance_low / support_high) are eligible as targets. Soft levels are deliberately excluded here: on 2026-09-08 SENSEX, VAL sat 6.1 points below spot while real support was 106.1 points away, which produced a nonsense 6-point target and a misleading EXPECTED_REWARD_INSUFFICIENT. Excluding soft levels from targets fixed it.
N. Position management1–19 minutes, hard forced exit at the limit. Fixed-order per-minute checks (time limit → minimum hold → target → stop → momentum failure → trail) so a minute in which two conditions fire records a deterministic reason. The stop may only tighten — see Snapshot 3.

R. Leakage tests (all pass)

Four properties are asserted: the decision uses no candle or option data after the 14:59 cutoff; post-14:59 data cannot create or change the initial decision; re-running the agent on a day whose decision is already frozen is a no-op that leaves the row byte-identical; and the recorded configuration hash matches the config actually used.

S. Real-order safety (12 tests)

  • Source scan of the whole paper_trading/ package: zero occurrences of place_order, modify_order, cancel_order, buy_order, sell_order, the Dhan broker client, or dhanhq. (This test once failed on a docstring that contained the literal string dhan_client — the docstring was reworded rather than the test weakened.)
  • No broker import anywhere in the package.
  • PaperBroker.__getattr__ raises RealOrderAttemptError for any execution-shaped attribute, so an accidental call fails loudly instead of silently.
  • The backend router set is GET-only; there is no write endpoint to attack.
Even if valid Dhan credentials are present in the environment, the paper engine has no code path that can reach an execution endpoint. There is no "Go Live" button, no feature flag that enables one, and no partially-built order function waiting to be uncommented.

T–V. Worked examples

T & U. Both real decisions produced so far are NO TRADE, shown in full in Snapshot 2. The NIFTY card is the clearest illustration of the gate order in action: the direction read was coherent (DOWN, five supporting factors), but the forecast expected move of 34 points was under 0.3× the 169-point ATR, so gate 7 fired and gates 8–10 were never reached — the agent never even looked for an option. That is the intended behaviour. A coherent direction is not sufficient reason to buy a decaying instrument for fifteen minutes.

W. Unresolved limitations

  1. The agent is very selective. A dry run across 22 historical symbol-days produced one trade (~5%). Five sessions may therefore yield zero trades. That is an informative result about the market and the gates, but it may leave the management path exercised only by rehearsal. I did not loosen any threshold to manufacture trades — doing so would have made the experiment meaningless.
  2. Day 1's decisions were frozen post-close, not live. The 2026-09-09 rows carry a 16:03 IST timestamp from a catch-up run using the correct 14:59 data cutoff. The data is right; the wall-clock freeze is not what a live session produces. Days 2–5 should be run through the live loop.
  3. P(NO MOVE) displays as 100% next to P(UP)/P(DOWN). The upstream CAS forecast keeps these as three separate tallies rather than one normalised distribution, so they do not sum to 1. This is pre-existing production behaviour surfaced by the new card, not introduced by 11D — and it is not "fixed" here because that would mean editing validated forecast logic inside a paper-trading milestone.
  4. Delta translation is linear (ignores gamma and IV changes) when converting an underlying level into a premium level. Realised P&L is always computed from actual quotes, never from this approximation — it only shapes the initial stop and target.
  5. All P&L is PRE-COST. No brokerage, STT, exchange or GST model exists in this project, so none was invented. A real net figure would be materially worse.
  6. The kill switch is CLI-only. The UI displays its state but cannot set it, because the API is read-only by design. That is a deliberate trade-off, not an oversight.
  7. Five Market Intelligence frontend files remain unused (2 components, 1 hook, 1 endpoint module, 1 types module) in the frontend tree (removed from the UI in bcbbf1d, files intentionally left in place). Harmless, but they are dead code until a future milestone deletes or revives them.
