Answer to C (the critical question): option 5-second data is used only AFTER the event detector has triggered. engine.evaluate_session calls detect_event (line 72) — which reads only the futures series — and returns early when it finds nothing (line 73). Only then does it call select_option (line 83) and confirm (line 85), which read the option quotes. No option field, and no index, OI, depth or futures-volume field, can cause or accelerate a detection. The option response is measured over the SAME 30 s window that the futures move used, ending at the detection bar.

Timestamps. Every series is keyed by bar_ts = start of the 5-second receive-time bucket (hr_capture/bars.py: “Bucketing uses receive time”). Futures/index use the bucket's last trade; option fields are “the last OBSERVED values as of bucket end” (hr_capture/option_state.py). 12A therefore treats a bar's values as known at bar_ts + 5 s; the HR writer lands them in the DB about 3.3 s later (median), which is why entry is modelled at the close of bar i+2.

Read the trace from the top. The selected CE started rising from about 15:00:20, from 109.60 up to 112.75, while the futures were still flat or choppy. The futures impulse (+12.9 points) came only in the 15:00:45 bar, so here the option led the futures by about 25 seconds. 12A notices only at the detection bar, looks at the option there for the first time, and fills 10 seconds later, after the option has already stopped rising.
Futures reference caveat (found in Part 2): the futures price 12A reads is the last trade. For SENSEX there was no futures trade in 84–95% of 5-second bars, so its last-trade price is stale and moves in jumps. 12A's staleness check (events.futures_stale) looks at quote updates (update_count), not trades, so it does not detect this. The captured futures bid/ask (hr_option_transition_state) is live but is not read by 12A.
